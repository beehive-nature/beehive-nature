    Which devices and keys can make your bzDiD: the full compatibility check
    The passkey must live in a PRF-capable authenticator: platform ones (Windows Hello, the Chrome profile, Google Password Manager, iCloud Keychain) work; most third-party managers (Bitwarden, 1Password & friends) don't yet. Create never takes a manager's word for it: after the "confirmed" the wallet immediately re-touches the exact passkey just made and demands a real PRF secret from it: if it can't, you're told plainly and that dead passkey should be deleted (Chrome: ⋮ → Passwords and autofill → Passkeys). A software passkey confirming instantly is fine; PRF is proven by the touch, not the speed. Hardware keys must be FIDO2.1-class with a PIN set and room for a resident credential. Older U2F keys won't be offered. If Windows said "unrecognized" when you inserted your key, use the dedicated 🔑 create on a hardware key button: it routes through the browser's native USB lane (no Windows passkey picker at all), which is the fix for exactly that error. Cross-device (the phone-camera QR) works only when the phone's provider has PRF: on the phone set the default passkey provider to Google/iCloud, or simply open this wallet on the phone itself. After a successful create, this wallet re-touches that same passkey automatically: no "which passkey?" picker ever again. Passkeys are origin-bound: one made at another site (an Anchor/wallet passkey for your account, say) can never connect here: it signs at its own site only. Your account's existing key still bridges you in via the bridge scaffold (not the New-bee primary path). Already hold a bzDiD elsewhere? Don't create a second.     🔐 the vault: one keypass, every secret

    Bringing keys you already hold: formats, and how they get sealed
    Gold path is connect / inject / derive / passkey — paste is scaffold · recovery only. The keys you already hold, seed phrases from any wallet (12 · 15 · 18 · 21 · 24 words) and Vaulta ACTIVE private keys (5K… · L… · K… · PVT_K1_…), are sealed under a single keypass so you never handle them raw again. Sealed with PBKDF2-SHA-256 ×600 000 → AES-256-GCM, header authenticated, salt and IV fresh on every write. Only the ciphertext is stored; it is safe to back up anywhere. Every phrase is checksum-verified before it goes in: a mistyped word is caught now, not on the day you need it.
    Stated honestly: this is hot storage. It ends the plaintext juggling; it does not turn a browser key into a cold one, and it cannot protect you from a page that has been tampered with. For balances you would not accept losing, the answer is still a signing device.
    Choosing your keypass: the one decision to take slowly
    ① Choose your keypass. This is the only thing standing between anyone with this browser and every secret inside. Generate one: eight words from the BIP-39 list is 88 bits of real entropy, which no one is brute-forcing. Write it on paper. There is no reset: lose the keypass and the vault is unrecoverable by design.

    Ways in.
    Each keypass and passkey here opens the vault on this browser, and none of them can read another.
    The vault itself lives only in this browser, so to open it on another device, save it as a file and
    import that file there with your keypass. The slot model: one random
    vault master key, wrapped once per keypass (PBKDF2) or passkey (PRF, HKDF), like LUKS keyslots. The slots live in
    this browser's copy (localStorage bnr_vault) and in each file exported from it; nothing syncs them, and a file
    imports through a keypass slot only.
    
    
    
    Evidence class follows T3 §6b — a credential is ranked by where its private key
    actually lives, not by brand. E3 = device-bound in a hardware keystore (Windows
    Hello, Apple/Google platform passkey on its own hardware, Bitwarden device-bound mobile).
    E2 = synced or software-held (iCloud Keychain / Google Password Manager / Bitwarden
    vault / a keypass in any manager) — only as strong as that vault account’s own auth.
    This page requests no attestation statement, so slots sit at the E2 floor unless you
    tell it the authenticator is device-bound.

    How each context gets its own key: derivation, on demand
  
    Every address here comes from your keys. Each context name derives its own key
  from your masterPRK: vaulta: for Vaulta account keys, evm: for 0x addresses, then
  sol:, btc:, ln: and nostr:; a name the wallet has no coin for is refused.
  hive: shows the public Hive account its active key named (same rail as balances).
  ar: is your Arweave address, a secp256k1 key under ar:<your name> (Arweave 2.9+);
  an RSA key never derives from masterPRK, and an address bound by hand or by an extension is
  only followed, never shown as yours.
  pq:ml-dsa-65 and pq:ml-kem-768 are your post-quantum public cards
  (FIPS 204 signatures; ML-KEM-768 + X25519 "X-Wing" so people can seal things to you),
  derived from the same masterPRK your recovery words carry, so those words restore them
  too. The signing card shows your self-certifying bzpq1 id; tap either card to
  copy your full public card (id, both keys, signature). The secret halves exist only while
  the keychain is connected and are wiped when it locks.
  Derivation is instant, free, deterministic: the same context always yields the same key on
  every device. We persist only the context list (this browser), never a key; keys exist
  only while your keychain is connected. Tap a key to copy it.

    How sealing works, and why it is post-quantum
    
    Sealing happens here, in this tab, before the file goes anywhere. Each file gets its
    own random 256-bit key (AES-256-GCM). That key is locked once per reader: for you, under a key
    your recovery words derive, with no public-key step at all; for each person you pick, under the
    X-Wing key (ML-KEM-768 + X25519) in the PQ card they gave you. The sealed file names no reader.
    A file you share carries your signature inside it, so only its readers learn it came from you;
    a file only for you carries none. Keep it anywhere, publish it, store it
    on Autonomi or Arweave: without a reader's words it opens for no one. To revoke, seal a new copy
    for new readers; someone who already opened a file keeps what they read. The binding button signs
    your classical addresses with your post-quantum id, co-signed by your bzDiD key, so you can prove
    later, even after a quantum break, which accounts were yours. Signing a file gives it a detached
    post-quantum signature (file.bpqsig.json) that anyone can check here, with no keys.
    Spec: SPEC-BPQ-1.
    
    
    Used the QR bridge before 4 October 2026? That older bridge sent your recovery
    root over public relays under a classical key exchange only, so someone who recorded it could open it
    once quantum computers arrive, and with it every key that root derives, post-quantum ones included.
    Make new recovery words, then, still connected with your old words, bind your new
    words: paste the new bzpq1 id into the binding field and bind, and the old id vouches for the new
    one while its keys still hold.

  the outbox persists, and nothing is called "sent" until the rail is read back.Mainnet signs with this wallet's derived K1 key only.
