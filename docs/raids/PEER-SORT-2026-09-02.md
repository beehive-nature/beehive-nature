**Sort rule.** RULE = runs with no operator-run box (on-chain contract, member-run client, pure
library, protocol/skill text). SERVER = needs a third party's hosted service.

**One-line verdict.** Peer's Base contracts are RULE and clean — no proxies, no seizure path on
deposits, referral split and post-intent hook already in the orchestrator. Everything that turns
a Venmo payment into a settlement is SERVER: one ECDSA signature from a Peer-held AWS KMS key,
minted by a Peer-run attestation service that replays the customer's authenticated request to
Venmo inside an enclave. No ZK proof is verified on-chain in the live path.

## 1 · The founder's picture, mapped onto the code (A69)

In zkp2p the party that receives USDC on-chain is the party that **paid fiat**. So:

| role | who at the salon | does | evidence |
|---|---|---|---|
| depositor / maker (LP) | a third party with USDC in escrow and a Venmo handle | receives the customer's Venmo; its escrowed USDC is released | `EscrowV2.createDeposit` `:147`, USDC `safeTransferFrom` `:1181`; `payeeDetails` `IEscrowV2.sol:70-75` |
| taker / onramper | **the customer** (or a relayer wallet acting for them) | `signalIntent` with `to = salon wallet`, then pays Venmo | `OrchestratorV3.signalIntent` `:112`; `to` at `IOrchestratorV3.sol:40`; `msg.sender` becomes `intent.owner` `:135` |
| recipient | **the salon** | signs nothing; receives one USDC `Transfer` | `_token.safeTransfer(_intent.to, netAmount)` `OrchestratorV3.sol:758` |
| anyone | relayer, customer, salon | `fulfillIntent` with the attestation | `:237-275` |

**The ONE seller-side call path: none.** The salon's wallet is a bare recipient; its single event is
an incoming USDC transfer from `OrchestratorV3 0x014025fDE093f8701d86e9f38e2C3a9b779cb5c7` (or from
a post-intent hook). If the estate instead plays depositor, it receives Venmo and its own USDC comes
home to itself — a fiat receipt, not new USDC.

**Where the post-settlement split (exact-multi + tithe) attaches — set by the taker at signal time:**
- `referralFees[]` — up to 10 recipients, ≤ 50 % total (`lib/ReferralFeeLib.sol:15-18`), paid from
  `releaseAmount` at `OrchestratorV3.sol:665-671` before `netAmount` goes to `to`. Tithe = one
  referral entry; seller = `to`. Caveat: a deposit protected by the gating service signs
  `hashReferralFees` (`:791`), so the LP's gating signer must accept the split.
- `postIntentHook` — any contract implementing `IPostIntentHookV2.execute(HookExecutionContext, bytes)`
  (`interfaces/IPostIntentHookV2.sol:36-39`); the orchestrator approves exactly `netAmount`
  (`:724-725`), the hook pulls it and splits. V3 whitelists **no** hook (`:529-533`); only V1 checked
  `PostIntentHookRegistry`.

## 3 · The notary question (A70)

**How the proof is made.** The PeerAuth extension (brand-neutral source in
`peer-examples/branded-extension/`) opens the payment-platform tab, watches `webRequest` for the
provider-configured URL, and packages **all request headers — Cookie and Authorization included —
plus the body** as "session material" (`src/entries/Background/buyerTeeCapture.ts:37-49`). It
encrypts that to an enclave key fetched from Peer (`buyerTeeSessionMaterialEncryption.ts:37-47`)
and hands the ciphertext to the host page; the SDK POSTs it to
`https://attestation-service.zkp2p.xyz/buyer/verify/:platform/:actionType` (`@zkp2p/sdk` 0.12.1
`dist/index.mjs:589-603`; `zkp2p-skills/shared/references/contracts.md:150`). The service decrypts
inside an AWS Nitro enclave, **re-issues the authenticated request to Venmo itself**, checks the
response, and signs an EIP-712 `PaymentAttestation`. On-chain, `UnifiedPaymentVerifierV3` checks
that ECDSA signature against a witness set of **one key, threshold 1** — `0xDB4Ed7FAF170F0f6493E3adaaCaaFaF47092c754`,
labelled "current AWS KMS signer" (`parameters.ts:61`); only staging lists a "Nitro TEE signer". There
is **no browser TLS transcript, no MPC, no proxy-mode zkTLS, and no ZK circuit** in the live path.
The skills repo calls this "the current TEE model" and lists the Reclaim fields as retired
(`create-zkp2p-provider/SKILL.md:21-38`; `references/runtime-contract.md:33-35` — "The attestation
service owns proof semantics"). V1 was different: circom circuits over DKIM-signed Venmo confirmation
emails (`zkp2p-v1-monorepo/circuits-circom/circuits/venmo`, `README.md:11`) and TLSNotary notaries at
`notary-us-west-1.zkp2p.xyz` for Wise/Revolut (`client/src/helpers/types/notarySettings.ts:8-17`) —
both gone from the live stack.

Two honest observations, recorded as boarding facts: the extension store-listing template says
"Your passwords, cookies, and session data never leave your device" (`templates/store-listing.md:34`)
while the code ships cookies encrypted to Peer's enclave; and the attestation README warns that a
leaked envelope "is therefore valid for the upstream session lifetime — treat any accidental
disclosure as equivalent to leaking the underlying upstream credential."

| question | answer | evidence |
|---|---|---|
| extension, MPC notary, zkTLS/TLSNotary? | Extension + **Peer-run enclave replay + KMS signature**. Not MPC, not TLSNotary, not a ZK proof | `buyerTeeCapture.ts:37-49`; `runtime-contract.md:33-45`; `UnifiedPaymentVerifierV3.sol:133-173`, `ThresholdSigVerifierUtils.sol:29-57` |
| who runs the attestor | Peer (zkp2p) — `attestation-service.zkp2p.xyz`, fallback proxy on Railway | `contracts.md:150-151`; SDK `index.mjs:447` |
| can a third party run one | Run the code, yes (MIT). Be **accepted on-chain, no** — witnesses are added only by the Safe | `MultiAttestationVerifier.sol:84-113` |
| RULE or SERVER | **SERVER** | A70 |
| what breaks the day Peer's notary stops | No new intent settles by proof (`fulfillIntent` needs a verifier success, `:237-275`). Locked intents have two exits, both on-chain rules: the **depositor's** `releaseFundsToPayer(intentHash)` (`:288-318`), or cancel/expiry back to the LP. A customer who already sent Venmo depends on the LP's goodwill; there is no permissionless alternative proof path. Unlocked LP funds withdraw normally | `OrchestratorV3.sol:237-318` |

## 4 · RULE-vs-SERVER sort

| component | RULE or SERVER | what it does | what breaks the day the hosting stops |
|---|---|---|---|
| **Contracts** (EscrowV2, OrchestratorV3, registries, hooks, StakeVault, IntentGuardian) | RULE | Escrow, intents, fee routing, referral split, post-intent hook, stake/dispute policy — all on Base, no proxies | Nothing. Deposits, intents, cancels, manual releases and withdrawals keep working from any RPC |
| **Verifier registry + UnifiedPaymentVerifierV3 + MultiAttestationVerifier** | RULE (contract) — **gating a SERVER key** | Checks one EIP-712 ECDSA signature from the Safe-managed witness set (threshold 1) | The contract runs, but its only accepted signer is Peer's KMS key; nothing new verifies |
| **Attestation / witness service** (`attestation-service.zkp2p.xyz`) | SERVER | Enclave replay of the customer's authenticated request + KMS signature | All proof-based settlement stops (§3) |
| **Browser extension** (PeerAuth; brand-neutral fork in tree) | RULE (client code, MIT) — useless without the SERVER | Captures the authenticated request, encrypts it to the enclave key (`GET /attestation?nonce=`) | Extension runs; capture fails at key fetch |
| **Core API** (`api.zkp2p.xyz`) | SERVER | `/v3/quote`, `/v2/makers/create|validate` (payee registration + hashing), `/v3/sign` (gating signature), `/providers/*` templates | Quotes/orderbook gone (chain readable via ProtocolViewer); gated deposits can't take new intents; SDK deposit creation fails (`sdk-api.md:83`) |

| **Indexer** (Envio HyperIndex `indexer.zkp2p.xyz`) | SERVER | GraphQL for intents/history; SDK `IndexerClient` | SDK history reads fail; on-chain views remain |
| **Dashboard / web app** (peer.xyz, pay.zkp2p.xyz, merchant.pay.zkp2p.xyz) | SERVER; NOT IN TREE | UI, checkout links, `PAY_API_KEY` webhooks | Checkout links + webhooks stop; contracts unaffected |
| **Relayer** | RULE (permissionless) + optional SERVER | `signalIntent`/`fulfillIntent` are callable by anyone; `RelayerRegistry` only grants whitelisted addresses multiple open intents | Nothing on-chain; users pay their own gas |
| **Price / quote** | SERVER (quote) · RULE (rates) | Rates live on-chain per deposit (`getEffectiveRate`, Chainlink/Pyth optional); best-quote matching via API + `orderbook.peerlytics.xyz` | Discovery degrades to reading the escrow directly |

## What stays behind (SERVER class — boarding facts, the dependency class the estate replaces)

Peer's attestation service and its single KMS witness key; the core API (quotes, payee registration,
gating signatures, provider templates); the Envio indexer; the dashboards and Pay checkout with its
API keys and webhooks; the Railway fallback proxy; the Peerlytics orderbook; the plugins that need
`ZKP2P_API_KEY` / `PAY_API_KEY` / `PEERLYTICS_API_KEY`. Two structural residues, stated once: **the
first mile depends on a third-party LP with a Venmo handle** (the salon cannot be its own LP and
still receive new USDC — A69), and **settlement finality is one vendor signature** until the estate's
own witness set exists (A70).
