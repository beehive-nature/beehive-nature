# bnr-seal — private receipt envelope, and the buzz agent-env companion

date 2026-09-27 · seat Claude · founder order: "do 1 then 2" (isolation, then private-receipt encryption)

## what landed here

`crates/bnr-seal`, one new workspace member. It holds a single AEAD suite that
seals bytes which are **already** a signed receipt, for private storage.

```text
canonical receipt bytes → issuer signature → bnr-seal envelope
```

- **Suite:** XChaCha20-Poly1305 via `chacha20poly1305 = "0.10"`. This is the
  crate, major version and AEAD primitive x0x already uses for encrypted KV
  records (x0x `a42b5d9`, `src/groups/kv_context.rs`:
  `GssKvSecureContext::seal_snapshot` fills a random 24-byte nonce with
  `rand::thread_rng().fill_bytes`, and `KvSecureContext::open` for
  `GssKvSecureContext` decrypts, both with AAD from `encrypted_record_aad` in
  `src/kv/encrypted.rs`), so the estate carries one AEAD primitive, not two.
  Only the primitive and nonce size are shared: x0x's key derivation and AAD
  format were not compared with bnr-seal's and are UNVERIFIED as equivalent. The lockfile adds `chacha20poly1305 0.10.1`,
  `chacha20 0.9.1`, `poly1305`, `aead 0.5.2`, `cipher 0.4.4` and their helpers.
- **Wire v1:** version (1 byte) · suite id (1 byte) · scope (32) · nonce (24) ·
  ciphertext and tag. The associated data is `bnr-seal/receipt/v1\0` followed by
  the first 34 bytes, so version, suite and scope are authenticated. They are
  readable, not encrypted, which is why the scope must be opaque and caller-derived.
- **Nonces:** fresh from the OS RNG on every seal (`seal` in
  `crates/bnr-seal/src/lib.rs`). No counter means no state to survive restarts
  or to share between concurrent jobs.
- **Rejections:** unknown versions and suites are refused before any
  decryption. A wrong key and a modified nonce, ciphertext or tag all return
  the same `Authentication` error on purpose. A changed version, suite or
  scope is a readable header field. It returns `UnsupportedVersion`,
  `UnsupportedSuite` or `ScopeMismatch` before decryption, which reveals
  nothing the envelope does not already show.

## what it does not establish

A successful `open` (`crates/bnr-seal/src/lib.rs`, `open`) authenticates only
that someone holding the same symmetric key produced the bytes for this scope.
That is sound by construction relative to the shared key, and no stronger. Whether the issuer is authorised, whether
the delegation is live, whether the work happened, and whether this is a
replay all stay with BNRoSe. The caller verifies the issuer signature on the
opened bytes. Key custody, key rotation and any KMS or bSAFE wiring are **not
built**. No existing x0x, storage or wallet protocol was changed.

  header layout, tampered ciphertext, tag and nonce, relabelled scope, scope

## companion lane (item 1): skaists/buzz#7

`buzz-acp` agents inherited the harness's entire environment. The draft PR adds
an opt-in `--agent-env-isolation` mode:

- agents start from an empty environment;
- they receive process essentials and the agent's own Buzz identity;
- operators forward anything else by name with `--agent-env-passthrough`;
- `--agent-cargo-home` sets a credential-free Cargo home, and startup refuses a
  directory that contains credentials.

The default stays inherit, because desktop-managed agents receive provider keys
through that environment. This isolates the environment only. It is not a
filesystem or network sandbox, and Codex's forced network access is unchanged.
