## 5. Interruption and replacement acceptance — exactly the named cases

The payer (`ant-pay.js`) already persisted, before each consequential step, the invoice identity and scope, the signed envelope and its hash, gas and quote reservations, the upload checkpoint and the retrieval reference, and reconciles an unknown broadcast from the chain by payer nonce. What was missing was a way for that record to leave a browser. `bpay-invoice.js` offers **"Save this file's payment record"** (schema `bpay.ant.journal/1`: the journal, never a key) and **"Open a saved payment record"** under *Limits & resuming*. This is state transport for the existing payer, not another executor, and a manual fallback, not the durability mechanism (see the OPEN item below).

**Covered, named by what each is** (`e2e/ant-replacement-recovery.mjs`, Arbitrum fixture, production keychain from source, chain and storage state kept in the test process outside every browser; green locally at this head):
1. **Same-context page restart after a lost receipt response** — the chain took the payment and answered the submission; every receipt query after it is withheld; the page is closed; a new page in the same browser profile resumes from the journal with no press and no send.
2. **Saved-record replacement** — the payment landed, the upload was lost, and the record was **saved before** the original browser was gone; a replacement client with empty storage opens it, the wrong file is refused, the right file resumes with no payment and no press, and the receipt names the original transactions.
3. **Already-stored, no-payment reuse** — no record anywhere; the network already holds the complete file; a stranger's client stores it and pays nothing.
4. **Lost submission acknowledgement, same context** — the chain took the payment but the submission reply never arrived; the page was closed while waiting; resume finds the kept hash on the chain and sends nothing. (New in this round; the earlier suite withheld receipts, not the acknowledgement.)
5. **Abrupt browser-process termination (SIGKILL) after submission, receipts withheld, delayed 12 s past the acknowledged write** — a persistent profile on disk; the browser process is killed, not closed; a new process on the same profile resumes from the journal with no press and no send. This establishes the **delayed-crash case only**. The 12 s is not a durability repair and is not presented as one.
6. **Abrupt termination immediately before the submission boundary** — the approval is on chain, the payment is on the keychain's card and unsigned; the kill loses nothing that was sent; the new process can only offer a fresh invoice and pays nothing without a press (the suite presses nothing). Whether the journal survived is measured and printed.
7. **Abrupt termination immediately after the acknowledged submission write** (within about a tenth of a second of `localStorage.setItem` returning) — the chain holds the payment; whether the browser's profile still knows it is **measured and printed, never assumed**. Measured on this box, 2026-10-13: the journal did **not** survive the immediate kill (case 6, killed before the boundary, lost its journal too, with nothing sent to lose). The new process offered a **new** invoice (2 planned transactions) for a payment the chain already holds, and paid nothing without a press — the suite presses nothing. That lost branch is the open case, shown, not hidden; a surviving branch would have resumed with no send, and the suite accepts either outcome only because it prints which one happened.

**The acknowledged persistence boundary, precisely:** the page's journal write is `localStorage.setItem` returning — the application's acknowledgement, synchronous in the page (`ant-pay.js` `save()`, called before every send marker and before every broadcast). Whether those bytes reach disk is the browser's business: Chromium commits DOM storage on its own timer, so an immediate kill can lose an acknowledged write. Measured on this box: 3 s after the write was not enough (the first run of case 5), 12 s was. That is a property of the browser, recorded here, not a diagnosis this lane claims to have proved beyond the measurement; the long-term acceptance boundary is "recoverable evidence durably acknowledged before an external effect", which no browser-local store meets.

**Not covered, and OPEN:** a paid-but-incomplete upload where **all original browser state is lost before any record was saved** (case 7's lost branch is exactly what it looks like). No fixture finishes it, nothing invents a payment to make it finish, and this dispatch does not count it. It needs an independently recoverable record acknowledged before the effect.

### 5c. Handed to the PR #411 owner — the operation format, the envelope-preservation rule, the reservations, the crash fixtures

What this lane hands over, as it exists on this branch, for the Rust core to consume or replace at its own pace (nothing here requires the wallet layer to land before this client repair merges):

- **The operation record** — `bpay.ant.journal/1` (`surfaces/bpay-invoice.js`, `refreshRecord` writes it; `checkedRecord` validates it): `{schema, testnet, exportedAt, artifact{name,sha256,bytes}, network{chainId,paymentTokenAddress,paymentVaultAddress}, ledger, claims}` where `ledger` is the payer's own journal (`ant-pay.js` `createHosted`): `{v:1, artifact, network, gasCeilingWei, plans[], checkpoint, result, receipt}`; each plan `{id, binding, scope, payer, payments[{quote_hash, rewards_address, amount_atto}], total, expiresAt, gasCeilingWei, authorization{invoice,scope,payer,expiresAt,gasCeilingWei,artifactSha256,at}|null, txs[], superseded?}`; each transaction `{kind: approval|payment, state: planned|sending|submitted|confirmed|failed|dropped, to, data, gas, maxFeePerGas, maxPriorityFeePerGas, reservedWei, nonce?, raw?, hash?, actualWei?, receipt?, block?, usedBy?}`. The plan `id` is the SHA-256 of `{binding, payer, txs, gasCeilingWei, created}`, the `binding` of `{artifact, network, payments}`, the `scope` of `scopeOf(artifact, network, plan)` — the existing BNR digest conventions, not a new one. A stable operation identity bound **before** signing, as the synthesis asks for, is the `scope` digest together with the plan `id`; what it lacks today is an authority epoch and an execution domain, which the Rust core's canonical intent should carry.
- **The envelope-preservation requirement** — before any broadcast the signed type-2 bytes and their locally computed hash are written (`t.raw`, `t.hash`, state `sending`), and after the submission reply the state becomes `submitted`; the kept bytes are re-checked by `AntPay._envelope.check` (decode, field-by-field comparison, sender recovery with noble secp256k1, chain id) before any re-offer, and identical bytes can only ever run once (`e2e/ant-hosted-purchase.test.mjs`: "a kept envelope no node took is offered again unchanged while authorized, never re-signed"; "unknown broadcast is discovered by payer nonce"). A replacement worker must hold `raw`, `hash`, `nonce`, the invoice (`id`, `scope`, `authorization`) and the quote bindings **before** the first broadcast, and reconcile that attempt from the chain; it must never generate a new payment because a response is missing.
- **The reservation rule** — `reservedWei = gas × maxFeePerGas` per transaction, held from `planned` until a verified mined receipt lowers it to `actualWei` or a nonce used by another transaction drops it (`ops/ant-extsig/src/budget.rs` is the Rust source of that rule; `gasExposure()` / `storageExposure()` in `ant-pay.js` apply it); quote claims (`bnr.ant.quote-claims.v1`) bind a quote hash to one file at send time and are derived from plans, never trusted from a file (§5a).
- **The crash fixtures** — `e2e/ant-replacement-recovery.mjs` cases 1–7 (named above) and `e2e/ant-record-import.mjs` cases 1–5, with the chain and storage state kept in the test process outside every browser, a persistent profile killed by pid (CDP `SystemInfo.getProcessInfo`), and the measured acknowledged-write boundary. The Rust core's own `crates/bnrose-exec-host/tests/recovery.rs` already drives crash-after-effect with UNKNOWN preserved; the fixtures here add the browser side (lost acknowledgement, lost receipt, kill before and immediately after the acknowledged write) and the destination-chain facts (Arbitrum's nonce, chain id and signed bytes) that a Vaulta-side record does not enforce by itself.

Explicitly not handed over as settled: any claim that a record on Vaulta prevents a second ANT payment on Arbitrum. The destination's own controls (chain id, nonce, calldata bound in the EIP-1559 signature) are what this lane's fixtures reconcile against; a Vaulta record the destination never checks is an audit record.

### 5a. The importer, repaired (the three reproduced defects, plus what the repair demanded)

The reviewer reproduced three defects in the importer at `404014891` with a copied handler body: an imported quote claim overwrote another file's claim; a failed claims write left the journal installed; a ledger whose `plans` was an object was accepted. All three now fail against the **real** browser handler in `e2e/ant-record-import.mjs`, and the repair treats a record as **evidence, not permission**:
- the whole ledger is checked for shape and consistency before anything is installed — v1, a list of plans, one paying account, the chosen file's identity, this page's network, every quote and total, the authorization fields, every transaction's kind, state, recipient, calldata (an approval goes to the token, a payment's calldata must encode the plan's own quotes), gas and fee quantities and reservation, and a receipt only for these bytes;
- every kept envelope (any transaction past *planned*) must carry its signed bytes and hash, and is **decoded and its sender recovered independently** by the same `AntPay._envelope.check` that gates a broadcast — a payer who did not sign it, a nonce the bytes do not carry, or a planned transaction claiming bytes is refused;
- quote claims are **derived from the record's own plans**, never read from the file, and a quote another file here already claims refuses the import;
- installation is **all-or-nothing under the purchase Web Lock** (`bnr-ant-purchase-v1`): a running purchase refuses the import; a quota or write error on the second write restores the first; an unreadable claims store refuses; an existing live record for the file is never replaced;
- asserted states are kept only as claims to re-verify: resume re-reads every non-planned transaction from the chain (`observe`) before any receipt; what the chain does not confirm stays **UNKNOWN** with its exposure and claim held, nothing re-signed, no replacement payment. The browser suite drives an asserted-confirmed record, its authorization window shut, against a chain that never saw it: the verdict is UNKNOWN by name and the reservation and claim are held. With the window still open the payer re-offers the **identical kept envelope** (same bytes, same hash, nothing re-signed) — the existing law that identical bytes can only ever run once, proven with an injectable clock in ; a browser run cannot reach that window deterministically because the payer first polls the chain for a minute per kept transaction.

**RPC wording corrected.** The fetch wrapper's generic "nothing was sent" was wrong for a submission: a failed `eth_sendRawTransaction` fetch now reports the outcome as **unknown** by name — the signed bytes, their hash and the reservation are kept, and resume reads the chain — while a failed read still says nothing was sent. A refused redirect is a refusal of that request, not evidence that the endpoint received nothing. Case 4 above exercises the lost-acknowledgement path end to end; the wording itself is covered by the same wrapper.
