## H01 — the four acceptance fixes

All findings were rechecked against the actual current source before
editing; none of the four had already landed. New implementation is
Rust in `crates/harness-sovereign`; bSigner's contract is unchanged;
no server database; no secrets in code, logs or this dispatch.

### H01A — Seed the task (`switch.rs`)

`SwitchCoordinator::run` now calls `seed_task_once` before the first
backend request: appends the tool contract (`system`,
`Toolset::system_prompt`) and the actual B9 user task (`user`,
`b9::b9_task_text(order_id)`), exactly once, only when the store is
empty (a resumed store is never re-seeded).
Regression `seeded_task_reaches_first_backend_once_and_survives_failover_byte_exactly`
uses a capturing backend wrapper that records the real request
message lists: the first request is exactly the seeded pair, and the
pair survives failover byte-exactly as the canonical prefix of the
second backend's request. The existing full-failover test's row
expectations were shifted by the two seeded rows.

### H01B — Handle exhausted backends (`switch.rs`)

`do_failover` now guards `active_index + 1 >= backends.len()` before
indexing the next backend: it freezes any partial text (marked
truncated), writes a `backend-exhausted` checkpoint, and returns the
new explicit `CoordError::BackendsExhausted` — no panic, no PASS.
The prober-flag path routes through the same guard. The coordinator
now accepts a single backend (assertion relaxed from ≥2 to ≥1) so the
single-backend case is constructible and testable.
Regressions: `single_failing_backend_exhausts_without_panic_or_pass`
and `complete_failure_chain_exhausts_with_evidence_preserved`
(failover happens, both frozen partials and both checkpoint phases —
`pre-switch`, then `backend-exhausted` — are preserved).

### H01C — Verify SAME ACTOR (`identity.rs`)

New `IdentityHook::verify_same_actor(pre, post, expected)` plus
`IdentityHook::public_material()` / `verifying_key()` and the free
`did_for_verifying_key()`: both checkpoint signatures verify against
the **same expected public key**; that key recomputes to the expected
DID via the canonical genesis binding (the `genesis` construction,
factored out and reused); both checkpoints must carry that DID; and
the post transcript must continue the pre transcript at a
complete-message boundary of the newline-joined canonical format.
`verify_continuity` is strengthened to route through the same checks
(same key, recomputed DID binding), keeping its signature.
Regressions: `same_actor_against_exported_material` (positive;
wrong expected DID, missing and malformed material, altered signed
bytes, and a mid-message prefix all refused) and
`other_key_with_copied_did_metadata_is_refused` (a different key's
genuinely valid signature with A's DID copied onto it is refused by
both entry points). One pre-existing test fixture
(`genesis_checkpoint_verify_roundtrip`) had its continuation bytes
changed to continue after the newline separator, matching the
complete-message rule it now exercises.

### H01D — Complete and independently verify B9 (`b9.rs`, new)

`b9.rs` pins the task: freeze the exact raw manifest bytes,
`input_sha256` over those bytes, `item_count` under a pinned record
definition (split on `\n`, strip one trailing `\r`, drop empty
records including the final terminator, duplicates count), sign
`<input_sha256>:<item_count>:<order_id>` through the existing bSigner
library interface (`IdentityHook::checkpoint`), represent the
signature as base64url no-padding via `bsigner::b64::b64u` (the
documented checkpoint-envelope representation), and write
`receipt.json` with `order_id`, `input_sha256`, `item_count`,
`signature`, `did`. `verify_receipt` / `verify_receipt_file`
recompute hash and count from the frozen bytes and verify the
signature against exported public material (which also binds the
DID). `accept_completed_run` fails acceptance for backend exhaustion
(an `Err` run), cancellation, and turn exhaustion, and `EndTurn`
without a verifying receipt also fails — `EndTurn` is not task
success. The receipt is separate from economic settlement.
Regressions: pinned count/payload and the empty-input SHA-256
constant; roundtrip production + independent file verification;
wrong hash/count/order/identity/signature and a foreign manifest all
fail; another actor's material and missing material fail;
acceptance gating across all run outcomes.

## H01 closing — acceptance and integration descendant (2026-10-29, later)

This section supersedes the completion claims above where they
differ. The earlier sections stand as the record of the first
candidate (`059e16f27`); this descendant holds merge while closing
the acceptance findings against it. H01A/H01B work and the improved
identity verifier are preserved unchanged in behaviour.

**1. Acceptance is bound to the requested order.** `verify_receipt`,
`verify_receipt_file` and `accept_completed_run` now take the
immutable expected order ID and reject a mismatch, and
`verify_receipt` rejects an unexpected `PublicMaterial.alg` (anything
other than `ml-dsa-65`). New regression
`valid_receipt_for_a_different_order_is_rejected` uses a genuinely
valid same-key/same-manifest receipt produced for ORDER-A while
ORDER-B is requested; `unexpected_public_material_alg_is_rejected`
covers `ml-dsa-44`, `ml-dsa-87`, `ed25519` and the empty string.

**2. B9 specification reconciled, not silently redefined.** Two
sources were read. Governing for the receipt: the Chain-of-Custody
statement in `hackathon-day1-submission-package-draft.md`
(SHA-256 `c391a3506eb3ac9ab0e0214e65af856efabae6df6fc7ef50354d266a1ea0721f` <!-- PUBLIC-CONSTANT -->)
— JSON manifest of ~40 biomass items, five-field `receipt.json`,
sign `<hash>:<count>:<order_id>`. Referenced by the old fixture

— a newline byte-ledger producing a different four-field
`result.json`. `b9.rs` now counts **JSON items** (top-level array, or

**3. The real execution path is connected.** `main.rs` freezes the
manifest bytes and establishes the expected order and public
identity material *before* model execution, all from one
`b9::RunDefinition` (saved goal, seeded task, order, verifier
expectations). It exports `public-material.json`,
`run-definition.json` and `frozen-manifest.bin` into the workdir.
The bounded `b9_receipt` tool (expected order only, frozen bytes
only, one shot) is exposed through the actual tool registry in
`tools.rs`, so the agent produces its receipt during the run. After
the run the executable exports `evidence/transcript.canonical.txt`,
`evidence/transcript.sha256`, `evidence/checkpoints.json` and
`evidence/run-outcome.json` (monotonic `duration_ms`), then routes
through `b9::accept_completed_run` — missing or invalid evidence
exits 3, coordinator failure exits nonzero, and no receipt is
generated after an arbitrary `EndTurn`. `--verify-only` re-checks a
finished run's artifacts from disk with no vault or keystore.
Backends remain configuration through the backend seat's existing
`OpenAiCompatBackend::new` constructor, now selectable with
repeatable `--backend-url` (plus `--backend-model` /
`--backend-key-env`); `backend.rs` was not edited and no newer
backend-seat seam had landed at inspection time.

**4. The actual binary is tested.** New integration suite
`crates/harness-sovereign/tests/b9_binary.rs` drives the built
executable against scripted loopback backends and reads artifacts
back from disk: zero turns (nonzero, no receipt), `EndTurn` without

definition (asserted in the binary test). The inherited UTC

`std::time::Instant`, never wall-clock differences.
