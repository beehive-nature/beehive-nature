# RAID — DECIMEN OPTICAL TRANSFER: screen-to-camera as a BNR onboarding + air-gap rail
**Source:** GitHub API source verification + decimen.app (2026-08-14); repo created 2026-07-30
**Doctrine:** L-VERIFY from repo, capture-pattern test, TAKE/LEAVE/PATTERN
**Prompted by:** founder — "it may produce something legendary... explore all ways to use this tech"; concern: "a new potential user doesn't have it installed"

## Executive Summary

Decimen is a real, well-built, screen-to-camera fountain-QR transport: no network, no pairing, no account, 64 MiB cap, SHA-256 verified before delivery, AGPL-3.0-or-later, ~2 weeks old, one maintainer. **It does not solve cold start** — a first-time *receiving* phone must load a camera-capable `https://` origin once, because both iOS Safari and Android Chrome deny `getUserMedia` to `file://` (`docs/user/install-and-offline.md`). Decimen is a *second-hop* technology: static QR carrying a URL → one network page-load → optical thereafter. The good news is the first hop is a page load, not an app-store install — which is exactly where WhatsApp/WeChat/banking apps are weakest. The highest-value BNR fit is not onboarding at all: it is an **air-gapped signing rung** between Pupa and Bee costing zero hardware, feeding the existing `POST /v1/upload` raw-signed-DataItem route. Most ceremony payloads BNR cares about (0.3–3 KB) fit in **one frame** and should be a static QR, not Decimen.

## Verdict

**PATTERN, with a narrow TAKE.**

- **TAKE (narrow):** the *unmodified* standalone sender (`decimen-v0.5.2-sender.html`, 226,647 B per the v0.5.2 release assets) as an air-gap egress appliance on an offline signing machine, and the unmodified hosted/self-hosted receiver as an ingest surface. Redistribute as-is with license banners intact; AGPL §13's source-offer duty is conditioned on modification (LICENSE line 540, verbatim FSF §13), and `build/license-banner.ts` already stamps every artifact with SPDX + a Source URL, so unmodified self-hosting is **compliant by construction**.

- **LEAVE:** vendoring current-main `shared/*.ts` into the wallet bundle. One import relicenses the combined work — bDiD code, ceremony journal, custody logic — as AGPL-3.0-or-later on first page load (§5(c) + §13). Fatal to an MIT ceremony surface.

**License path — the corrected picture.** Prior BNR analysis framed this as *self-host AGPL vs. reimplement in Rust*. Two facts change the menu:

There is a complete, working, MIT-licensed optical transport BNR can vendor into MIT code **today**. Ceiling: it is wire v1 (magic `0x0C`), so it cannot interoperate with any current Decimen user — by design, loudly.
2. **The protocol is published as an implementation-independent contract and second implementations are explicitly invited.** `docs/technical/versioning.md` opens: *"This is the format contract, independent of any one implementation."* `docs/technical/golden-vectors.md` is titled conformance data for a non-TypeScript client. A clean-room Rust implementation from those two docs is very likely lawful and not a derivative work (17 U.S.C. 102(b); *Google v. Oracle*) — **NEEDS LEGAL CONFIRMATION, this is not legal advice.**

Recommended sequencing: **self-host unmodified now** (Path B) for any real flow; **fork MIT v0.3.0** as a frozen MIT reference to bootstrap from; **clean-room Rust wire-v3** later if and only if a Rust signer needs it. Do not vendor AGPL `shared/` into the wallet.

## What It Is (verified)

**Frame format** (`shared/protocol.ts:61-127, 403-418`). 22-byte little-endian header + `blockLen` payload: `[0]`=0xD1, `[1]`=0xC3, `[2]`=version (WIRE_VERSION=3), `[3]`=flags, `[4:6]`=sessionId u16, `[6:10]`=seq u32, `[10:12]`=k u16, `[12:14]`=blockLen u16, `[14:18]`=totalLen u32, `[18:22]`=payloadFnv u32. **No file metadata in the frame header** — filename, MIME and SHA-256 live only in the inner container and arrive only on full reassembly. Two magic bytes answer "is this ours" before any version is named; `0x0C`/`0x0D` are reserved forever as v1/v2 markers so a v3 receiver names an older sender rather than shrugging. `flags` splits `0x0F` must-understand / `0xF0` safe-to-ignore.

**Container** (`shared/protocol.ts:126-127, 262-363`). 49-byte `DCF2` header: magic, compression byte (0=none, 1=gzip, >1 rejected), nameLen u16, typeLen u16, fileLength u32, transmittedLength u32, SHA-256 (32 B), then name, type, payload. Overhead is exactly **49 + len(filename) + len(mimetype)** — verified arithmetically against the benchmark receipt (1048576 + 49 + 13 + 9 = 1048647 = `payloadBytes` in `benchmarks/records.json`). A pasted text snippet pays a flat **91-byte** tax (`snippet.txt` = 11, `application/vnd.decimen.snippet` = 31).

**The fountain is not what the docs say** (`shared/fountain.ts:130-178`). The shipped v2/v3 stream is a **systematic carousel**, not robust-soliton LT. `cycleLength(k)=2k`; positions `0..k-1` emit source block `[pos]` directly; positions `k..2k-1` emit repair frames with **uniform** degree drawn from 4..24 (`REPAIR_DEGREE_MIN/MAX`). The soliton machinery is retained and golden-tested but the source comment at lines 170-173 states it "is no longer emitted." `docs/technical/protocol.md:9` and the README still describe robust-soliton LT. **A second implementation built from the prose ships a non-interoperable sender.**

**The README's ~K×1.15 overhead figure is stale, and the code and the receipts disagree with each other too.** `shared/progress.ts` states 1.15–1.6 was the v1 soliton fountain; the v2 carousel needs exactly 1.00 at zero loss (p50 *and* p90 over 100 trials at k ∈ {5,25,100,400,1600}), and `expectedFountainOverhead()` returns a flat 1.02. But the two real receipts measured **1.20** (desktop→phone, framesNew 428 / k 358) and **1.30** (phone→phone, 464/358). **Plan BNR capacity against 1.3.**

**Capacity per frame.** `blockLength(frameBytes) = frameBytes − 22`. Six offered sizes → payload: 500→478, 1000→978, 1465→1443, 1850→1828, 2331→2309, **2953→2931** (default; QR V40 byte-mode at ECC L). k is a u16 (`MAX_SOURCE_BLOCKS = 65535`), so the 500 B setting tops out at ~30 MB, not 64 — `fitsInOneStream()` pre-checks and `smallestSufficientFrameSize()` names the fix rather than failing mid-stream.

**Measured rates — and the caveats that matter more than the numbers.** Channel model, validated against both receipts: raw = txFps × gridCodes × frameBytes; goodput lands at 0.58–0.60 of raw. Desktop→phone record **418.5 KB/s** (4 codes @ 60 fps, acq 0.11 s); phone→phone **199.2 KB/s** (2 codes @ 60 fps, acq 0.26 s). Three caveats:
- **Both receipts are wire-v2** (`blockLen` 2933 at appVersion 0.4.0 ⇒ 20-byte header). No record in `benchmarks/records.json` was measured on the shipping wire format.
- **The shipped default is 1 code**, not 4. `send/index.html` defaults to 1; benchmark mode presets 4. Projected default ≈ **104.6 KB/s** — the README badge overstates out-of-the-box performance by ~4×. *(Extrapolated, never benchmarked.)*
- **The 60 Hz cliff.** `shared/send-settings.ts` documents that at 60 fps on a 60 Hz screen each frame gets one refresh cycle, with "early field runs there measured 0.2-0.4 catch rates." Most monitors in the world are 60 Hz. Projected: ~39.6 KB/s at catch 0.30; the documented no-signal fallback (24 fps / 1465 B) at catch 0.85 ≈ **24.0 KB/s**; a cheap camera with hand tremor ≈ **5.3 KB/s**; slowest UI-offered settings ≈ **3.3 KB/s**.

**Acquisition is the floor for everything small.** Camera-start→first-decode is 0.11 s / 0.26 s in the receipts. Any payload of 1–4 frames finishes in 17–67 ms of transmission. **Below ~50 KB, making the payload smaller buys nothing measurable.**

**Pure static, confirmed.** `package.json` has **no `dependencies` block at all** — 9 devDependencies, and all 426 `package-lock.json` entries carry `"dev": true` (clean 1:1). No server directory, no API route, no edge function in the 100-file tree. Exactly three `fetch()` calls touch a reporting endpoint (`send/main.ts:514`, `send/main.ts:601`, `receive/main.ts:1018`), all POST to relative `/__diagnostics`, all wrapped in `import.meta.env.DEV && import.meta.env.VITE_DIAGNOSTICS === "1"`; the sink is a Vite plugin with `apply: "serve"`. Both halves are structurally incapable of shipping. Grep across every page and entry module for `analytics|gtag|plausible|umami|posthog|sentry|matomo|WebSocket|EventSource|sendBeacon` returns **nothing**. The only other `fetch()` is `send/main.ts:248` loading bundled demo PNGs by relative path. Live `sw.js` on decimen.app references no external origin.

**The hash gate is correctly placed** (`receive/main.ts:939-944, 1103-1166`). Order: fountain completes → `assemble()` → `fnv1a(payload) === header.payloadFnv` → `unpackFile()` structural checks + gunzip → `verifyFile()` SHA-256 → **only then** blob URL, download anchor, `previewElement()`, `showSnippet()`. All rendering sits inside the try block after line 1106. **A malicious sender cannot make the receiver render or play anything before the hash gate.**

**Gzip bomb handling is better than most production code** (`shared/protocol.ts:161-194, 335-349`). `gunzipAsync` takes an explicit `maxBytes`, counts bytes off the `DecompressionStream`, and cancels + throws `inflateOverflow` at the ceiling. The comment states the trailer's declared size is attacker-controlled and "a hint, never a bound." Three checks stack: trailer ISIZE must equal container `fileLength` *before* inflation, `fileLength` must be >0 and ≤ MAX_FILE_BYTES, post-inflate length is re-checked. `maxBytes` passed is `fileLength`, not the 64 MiB ceiling.

**CI enforces the architecture** (`.github/workflows/ci.yml`): exactly one `dist/assets/receive-*.js` chunk under 24,000 bytes ("a regression here means the inlined worker or wasm leaked into the served bundle"); every page's manifest/SW reference must resolve to a file on disk (a real past bug); the README benchmark table must still match `benchmarks/records.json`. Unusually disciplined for a 2-week-old repo.

## The Security Frame

**Integrity yes; authenticity no.** `verifyFile()` (`shared/protocol.ts:365-368`) compares SHA-256 of received bytes against the 32 bytes at container offset 17 — **which the sender wrote**. It is a transport checksum, not an attestation. `fnv1a` is a non-cryptographic 32-bit framing check. There is no signature, no key material, no nonce, no timestamp, no challenge, and **no replay protection anywhere in the format**. Frames are stateless and the carousel loops forever, so **a recorded video of a sending screen replays as a perfectly valid transfer.**

**The extension point is already carved — this is the most BNR-relevant fact in the repo.** `FLAG_ENCRYPTED = 0x01` is declared CRITICAL, never set by this build, and deliberately **not** in `SUPPORTED_FLAGS` (=0x00), so a stream claiming encryption is rejected loudly with an `unsupported-flags` verdict rather than silently mis-decoded. Three more must-understand bits (`0x02`/`0x04`/`0x08`) are unclaimed. A "signed ANS-104 DataItem" profile as flag `0x02` is a **flag, not a wire-version break**, and every deployed v3 receiver already knows to refuse it out loud. That loud, specific, non-silent failure mode is the whole reason the v3 break was spent. *(Caveat: claiming a bit is still a wire change relative to upstream and would need upstream buy-in or a fork.)*

**What must be layered on before this carries anything identity-shaped:**
1. **Ed25519 verification by the receiving ceremony**, against a key the receiver already trusts (bDiD document / prior journal head) — **never** against anything in the frame. Treat `unpackFile()` output as untrusted bytes and the container SHA-256 as a CRC.
2. **Freshness / anti-replay**: bind every payload to a challenge the receiver generated. The hash-chained ceremony journal head is the natural challenge. The wire carries no nonce, no timestamp, no counter.
3. **Never optically transmit** a private key, BIP-39 mnemonic, JWK, or IndexedDB-wrapped key blob. A wrapped payload, if ever needed, carries its own AEAD *inside* the container and must not rely on `FLAG_ENCRYPTED`, which this build refuses.
4. **Bound `totalLen`** before adopting receiver code (see hazards).
5. **MIME allowlist** — never hand `file.type` to a Blob constructor or a Response header.
6. **Serve ceremony surfaces with a real CSP.** decimen.app has none (verified live).

**What runs before the hash gate** (the pre-auth attack surface, reachable by anyone who can put a QR in camera view — a poster, a shared screen, a video): the vendored 281,113-byte WASM QR decoder chewing attacker-controlled pixels; `classifyFrame`/`parseFrame`; LTDecoder allocation and XOR peeling; `assemble()`'s full-payload allocation; `fnv1a` over the whole payload; and gzip inflation inside `unpackFile()`.

**Filename handling is defensive on both ends** (`shared/protocol.ts:196-211`). `safeFileName()` takes the basename, strips C0 controls and DEL, trims, maps `''`/`.`/`..` to `transfer.bin` — applied in `packFile` *and again* in `unpackFile`, with the comment that the receiver "has no reason to take the sender's word for it." Snippets decode with `new TextDecoder('utf-8', { fatal: true })`.

**Render surface is narrowly gated, and that gate is load-bearing for BNR.** `isPreviewable()` (`receive/main.ts:1187`) matches only `image/`, `video/`, `audio/` prefixes. Images go to `<img src=blobUrl>` (SVG in `<img>` is script-free per spec); video/audio go through `servableMediaUrl()` into the Cache API at `/received-media/current`. Because the cache write is *downstream* of `isPreviewable`, the stored Content-Type is constrained to `video/*|audio/*` — HTML cannot be planted there. No `innerHTML` anywhere in `receive/main.ts`; every string goes through `textContent`.

**The "no network" claim survives audit.** Standalone builds additionally make it **browser-enforced**: `build/standalone-csp.ts` injects `default-src 'none'; style-src 'unsafe-inline'; font-src 'none'; base-uri 'none'; form-action 'none'; script-src 'unsafe-inline' 'wasm-unsafe-eval' blob:; worker-src blob:; connect-src data: blob:; img-src data: blob:; media-src blob: mediastream:`. No `http(s)` source appears anywhere in the policy. The plugin's own rationale: *"The point is not XSS — it is making 'no network' enforceable instead of merely intended."*

**The single biggest clean-room trap is the deterministic logarithm.** `docs/technical/protocol.md`: sender and receiver must build bit-identical distributions, JS engines disagree about `Math.log`, and `fountain.ts` therefore ships a deterministic log from exactly-specified IEEE-754 ops — *"V8 vs JavaScriptCore desync is a silent, total failure mode."* The header calls it a "Determinism warning that cost a debugging session" and documents `dlog` as "exact-ops range reduction + atanh series", "Exported only so tests can pin it. **This is wire format, not a utility.**" A Rust reimplementation must reproduce it bit-for-bit or every transfer silently fails. **Contamination risk is concentrated in exactly this one function, where the temptation to peek is maximal and copying would be most visible. Firewall personnel assignments in writing before any Rust work starts.**

## The BNR Use-Case Map

**The crossover number that reorganises everything:** at the default 2953 B frame and a 22-byte header, one frame carries **2931 payload bytes**. Any payload ≤ ~2.9 KB is **K=1** — a plain **static QR** carries it with zero moving parts. Decimen only starts earning its place above ~3 KB and only really pays above ~30 KB. Run every proposal through this filter.

Times below are: **[A]** 418.5 KB/s desktop→phone record / **[B]** 199.2 KB/s phone→phone record / **[C]** ~104.6 KB/s shipping default *(extrapolated)* / **[D]** 20 KB/s pessimistic — container tax, k×1.02 frame floor, and acquisition included.

**Rank 1 — Air-gapped signing loop as a free custody rung. VALUE 5 / FEAS 3-4.**
Payload out: unsigned tx or ANS-104 DataItem preimage, 100 B–256 KiB. Payload back: detached Ed25519 sig (64 B) or the full signed DataItem. **Displays/scans:** both directions, so both devices need a camera *and* a served https origin — that is the feasibility cost. **Signing:** both directions must be signed; the outbound request needs its own authentication so the offline signer renders *what-you-see-is-what-you-sign* rather than blind-signing whatever a hostile screen shows. **Times:** 4 KB tx = 0.12 / 0.29 / 0.25 / 0.60 s; 256 KiB DataItem ≈ 0.63 s [A], 1.3 s [B]. **No-install story:** offline phone runs the BNR PWA in airplane mode — already installed by definition, so this use case is *immune* to the cold-start problem.
*Why it matters:* `crates/wallet-relay/src/ladder.rs` jumps from Pupa (T-F verification, FIDO2 key you must buy) to Bee (T-H custody, Trezor you must buy). An offline second phone inserts a T-H-grade rung at **zero hardware cost** — what a 10^10-user filter with no subsidy actually requires, and consistent with hardware being a preference, never a credential (RELAY_17).

**Rank 2 — Offline signer → light → networked browser → `POST /v1/upload`. VALUE 5 / FEAS 4.**
`crates/wallet-relay/src/lib.rs:53` already routes a body documented as "one raw user-signed Ed25519 DataItem", and the relay never holds keys. **This is a complete air-gapped Arweave publishing pipeline requiring no new relay surface at all** — the single cleanest Decimen fit in the BNR tree, and above the crossover for any DataItem carrying real data. `PHASE0_AR_ANT_SETUP_SPEC` routes payloads under 256 KiB to Arweave; that is 0.63 s [A] / 1.3 s [B].

**Rank 3 — Cross-device ceremony resume, the anti-FlowToken. VALUE 5 / FEAS 5 / DECIMEN-NECESSITY 1.**
Payload: `{v, designation, step_id, journal_head_hash, subject_bdid, nonce, expiry, sig}`, ~0.5–2 KB = **one frame**. **Displays:** the desktop that started the ceremony. **Scans:** the phone. **Signing:** must be signed by the originating device's key and bound to the journal head, with nonce + short expiry. **Must never cross:** serialized plan context containing key material, or anything the receiver deserializes into code — the direct answer to the FlowToken do-NOT-transfer row (`pickle.dumps` → base64 → DB text, `pickle.loads` on a URL parameter). **Times:** 0.11 / 0.27 / 0.22 / 0.53 s. **Verdict: build it — as a static QR.** Decimen is strictly more complexity (AGPL dependency, camera pipeline, fountain decoder, worker pool) for a single-frame payload. Reach for Decimen only if the resume document ever carries an attachment.

**Rank 4 — Desktop→phone onboarding handoff. VALUE 5 / FEAS 5 / DECIMEN-NECESSITY 1-2.**
Same payload class, same "static QR" verdict. **Constraint:** `DISPATCH_BNR_INVITE_ONBOARD_2026-08-08` item 6 explicitly says do **not** gate invite joins behind a desktop-pairing wall — so an optical desktop→phone hop is always an *accelerator* with a typed-URL fallback, never the only path. Item 4 (idempotent re-open: **resume, not re-consume**) is the correctness property the resume document must carry.

**Rank 5 — Watch-only wallet provisioning. VALUE 4 / FEAS 5. A genuine Decimen fit.**
Payload: JSON array of `WatchAddress {rail, address, label, custody}` per `crates/wallet-relay/src/watch.rs` — public data, a few hundred bytes each, so ~100 addresses ≈ 20 KB. **Displays:** the Trezor-connected desktop. **Scans:** the phone. **Times:** ~0.16 / 0.36 / 0.41 / 1.4 s. **Signing:** must be signed by the account's bDiD key — an unauthenticated watch-only list is an **address-substitution primitive**, and the receiving UI will happily render an attacker's address as "your receive address." **Must never cross:** an xpub. Not a private key, but broadcasting it to every camera in the room hands an observer the entire present and future address tree. Individual addresses only. **Structural bonus:** today `WATCH_ONLY_ADDRESSES` is an env var an *operator* sets on the relay; a user-signed optical import removes the operator from the loop entirely — a direct filter win.

**Rank 6 — Mesh-down revocation / rotation publication. VALUE 4 / FEAS 4.**
Sign a revocation entry offline, flash it to any networked device willing to anchor it. Operationalises the revoke-ordering technique (publish and anchor the revocation entry **before** tearing down the old key's live capabilities, so nothing can be minted mid-revocation) under exactly the conditions where the network path is the thing that failed. Small payload, high urgency; a static QR also serves.

**Rank 7 — Offline / venue / kiosk onboarding. VALUE 4 / FEAS 3.**
Live context exists (`RECEIPT_FIRSTLIGHT_VENUE_2026-08-14`: external ingress blocked at the OCI layer). Three constraints bite: (a) the receiving phone needs a camera-capable secure origin, so the venue must serve over https with a **real** certificate — self-signed forces every attendee through a security warning, unacceptable at a 420-person event; (b) Decimen's own docs say demo mode "is not a hardened kiosk: anyone with the keyboard has devtools"; (c) a venue is the **worst** environment for an unencrypted channel.

**Rank 8 — Full DID log replication. VALUE 3 / FEAS 4.**
50 KB: 0.23 / 0.51 / 0.68 / 2.9 s. 500 KB: 1.30 / 2.77 / 4.98 / **25.4 s** (and ~95 s at a 5.3 KB/s bad-camera floor). Attended and deliberate, not background sync. JSON gzips well, so real times beat the table by an unmeasured factor.

**Rank 9 — Hash-chained journal / receipt export to an auditor's laptop. VALUE 3 / FEAS 5.**
Grows monotonically into megabytes; public-by-design, so non-confidentiality is a non-issue. **Cheapest real win on the board.**

**Rank 10 — Signed ops-artifact distribution to air-gapped machines. VALUE 3 / FEAS 4.**
AAGUID→tier snapshots, NixOS configs, pinned gateway lists — signed, verified on arrival against a pinned key, well above the crossover.

**Rank 11 — Transferring the PWA bundle itself. VALUE 5 if it worked / FEAS 2.**
**Broken in the direction you most want.** A bundle flashed onto a phone lands as a `file://` page with **no camera** — you cannot bootstrap a *receiver* onto a phone this way. What works: the standalone *sender* is 226,647 B and works from `file://` everywhere, and desktop Chrome/Firefox generally prompt for camera from `file://`. **The working shape is bundle→laptop, not bundle→phone.** Cost even where it works: Decimen's own 992,317 B receiver is 2.43 / 5.13 / 9.46 / 48.9 s (≈3 min on a bad camera); the 4,373,502 B site zip is 10.3 / 21.7 / 41.0 / 214 s. A 200 KB–1 MB wallet PWA (Decimen's 226 KB sender proves a real app can be that small) is 0.6–2.4 s measured, 11–49 s pessimistic. **Never ship it as a .zip** — `packFile()` skips gzip for precompressed types, so a zipped wallet pays full freight.

**Rank 12 — Paper / QR delegation packets. VALUE 3 / FEAS 1. Recommend a plain no.**
Decimen is an **animated** stream; it cannot be printed. There is no paper story here. A printed delegation packet is a set of static QRs and is a different technology — do not let the fountain-coding elegance pull this into Decimen's orbit.

**Reusable asset, not a use case:** Decimen's 12-language localisation including RTL layout is the same problem BNR onboarding must solve.

## The Chameleon Angle

**The structural asymmetry you must design around.** WhatsApp Web QR login, WeChat pay QR, and banking-app pairing all *look* like optical ceremonies and are not: in every case the QR is a static pointer and the ceremony completes over a **server-mediated back-channel** (phone ↔ vendor server ↔ browser). Decimen has no back-channel by construction. BNR therefore cannot mirror these one-for-one with a single optical hop. Two honest options:
- **(a) The double-flash.** A displays, B scans; then B displays, A scans. Strictly **more sovereign** than the incumbent — no server exists at any point — at the UX cost of a webcam on the desktop.
- **(b) One-way push**, where the scanning device ends up holding the artifact and no return leg is needed.

Design the funnel around **(b)** wherever possible; reserve **(a)** for high-value ceremonies.

**Banking-app pairing — the direction reversal that makes it safe.** Incumbents show a QR on the *already-trusted* device and have the *new* device scan it. **BNR must reverse this:** the new device generates a keypair and **displays its `pubkey_envelope`** (the exact shape already in `crates/wallet-relay/src/envelope.rs`), and the trusted device **scans it** and signs the additive enrolment entry into the hash-chained log. Reversing the direction means no secret ever leaves the trusted device and the public channel only ever carries a public key — **the only version of this ceremony that is safe on an unencrypted channel.** Maps onto the existing `POST /v1/bni.id/enroll` route.

**WeChat-style payment — the most novel mirror.** Merchant displays a signed invoice; customer scans, signs a payment authorisation entirely offline, displays it back; merchant scans and broadcasts whenever it next has network. A complete offline payment ceremony with no acquirer, no processor, no server — a thing WeChat structurally **cannot** do. High strategic value; presumes a BNR offline payment ceremony that does not exist anywhere in the tree today.

**The onboarding funnel, honestly.** The sender's share dialog draws a QR of the receiver URL (`shared/share-dialog.ts` + `send/index.html:112`) — a new user points their stock camera app at the screen, taps the notification, and is in a working receiver in one hop. No app store, no install, no pairing, no account. **But the real bootstrap chain is: static QR on a poster/screen carrying a URL → one network fetch of the PWA → Decimen for the payload.** Decimen is a second-hop technology. The genuinely good news is that the first hop is a *page load* rather than an app-store install — precisely where the incumbents are weakest. **So the no-install story is real; it is just one hop later than the framing assumes.**

**The WebAuthn consequence bounds the entire map.** A WebAuthn credential is permanently bound to a DNS name someone must keep controlling, and therefore must **not** be the identity root — it is a device-local unlock factor gating the user-held key that *is* the bDiD root. A passkey is non-exportable and origin-bound, so it can **never** cross an optical channel, encrypted or not. Combined with `DESIGN-BRIEF-03` Tier 1 (signing key encrypted in IndexedDB, unlocked by passkey assertion), **the exhaustive list of what may cross** is: the bDiD identifier; signed ceremony/resume documents; public keys and addresses in versioned envelopes; unsigned and signed transactions/DataItems; journal entries and receipts; and the app bundle. Adding a second device is therefore always either **re-derivation from the seed locally** or **additive enrolment of a new authenticator** — never a key move. **Decimen carries the enrolment request, never the key.**

## What Does Not Transfer / Hazards

**CONFIRMED, HIGH — unbounded `totalLen` is a one-frame, pre-hash-gate memory DoS.** `classifyFrame` (`shared/protocol.ts:456-463`) rejects only `k===0`, `blockLen===0`, `totalLen===0`, and requires `bytes.length === 22+blockLen`. **`totalLen` is a u32 with no upper bound and is never compared against `MAX_FILE_BYTES` anywhere in the receive path** (grep for `MAX_FILE_BYTES` in `receive/main.ts` returns nothing). `receive/main.ts:927` constructs `new LTDecoder(header.k, header.blockLen, header.sessionId, header.totalLen)` straight from the header, and `fountain.ts:315` does `new Uint8Array(this.totalLen)`. A **single hostile QR code** with k=1, small blockLen, an even seq and `totalLen=0xFFFFFFFF` completes the decoder on frame one and triggers a ~4 GiB allocation; if it succeeds, `receive/main.ts:942` then runs `fnv1a` over 4 billion bytes **on the main thread**. `assemble()` at line 940 sits **outside** the try/catch (which starts at line 1103 inside `finish()`), so a `RangeError` is uncaught. Cost to the attacker: one printed QR code in camera view. `tests/protocol.test.ts` contains no bound test for `totalLen`. **Fix before BNR adopts this code: enforce `totalLen <= MAX_FILE_BYTES` and `totalLen <= k*blockLen` in `classifyFrame`.**

**Attacker-chosen MIME on a same-origin blob URL, on an origin with no CSP.** `receive/main.ts:1138` passes the sender's arbitrary type string (up to 65535 bytes, no allowlist, only empty-string defaulted) into `new Blob([bytes], { type: file.type })` for **every** received file. The anchor carries `download`, so an ordinary click saves rather than navigates — but the blob URL is same-origin on `https://decimen.app`, and **that origin has no Content-Security-Policy** (verified live 2026-08-14: `curl -sI https://decimen.app/receive/` → 200 OK, Server: GitHub.com, no CSP header; GitHub Pages cannot set response headers, and `build/standalone-csp.ts` is applied only to standalone builds per `vite.config.ts:132`). If that URL is ever navigated to — open-in-new-tab, a future code path dropping `download`, a share-sheet integration — a `text/html` payload would execute script in **the origin that owns the service worker and the received-media cache**. A MIME allowlist at the container-unpack boundary closes this permanently.

**The hosted/self-hosted build has no CSP at all.** `standalone-csp.ts` is explicitly standalone-only "because the hosted site legitimately fetches its own assets and a service worker." A `transfer.bnr` deployment gets **zero** CSP unless BNR writes one at the web-server header level. **This is the single biggest gap between the repo's stated posture and what a self-host actually gets.**

**`VITE_SITE_URL` is a self-host trap, and the config comment is wrong about it.** `vite.config.ts` claims SITE_URL is "used only to make the social-card URLs absolute... nothing else depends on it." **That is false.** `%SITE_URL%` is also baked into `send/index.html:112` (`<input id="share-url" readonly value="%SITE_URL%receive/">`) and `index.html:109`, and `shared/share-dialog.ts` draws the QR from `urlInput.value`. **If BNR builds without `VITE_SITE_URL=https://transfer.example/` (trailing slash required), the sender's "Share the receiver" QR sends every new user's phone to decimen.app/receive/** — off-property, third-party-hosted, at the exact moment of onboarding. Precisely the funnel that matters.

**Banner stripping turns compliant hosting into a violation.** `build/license-banner.ts` uses `/*!` comments (minifier-preserved) and an HTML comment after the doctype — but an aggressive post-processor, HTML rewriter, CDN optimizer, inliner, or re-bundle of `dist` can drop them, breaching §5(a) and §7 on an otherwise-clean unmodified deploy. **Add a post-deploy assertion** that served JS/CSS/HTML still contain `SPDX-License-Identifier: AGPL-3.0-or-later` and the Source URL.

**Rebrand surface is wider than `VITE_SITE_URL`.** Hardcoded upstream identity lives in `build/license-banner.ts` (the `https://decimen.app` and `Source: github.com/bashalarmistalt/...` strings are **hardcoded, not tokenized**, and `VITE_SITE_URL` does not touch them), the footer copyright/AGPL link and "♥ support" buymeacoffee link on all three pages, `receive/support.ts:11`, `build/rewrite-standalone-links.ts:74`, `public/robots.txt`, `public/sitemap.xml`, the manifest name/short_name/description in `MANIFEST_BASE`, and the icon set. A rebrand leaving the banner pointing upstream is **both misleading and non-compliant**. `npm run icons` needs librsvg and does exact-match surgery that throws if the logo changes shape.

**Redistributing builds pulls in the vendored WASM.** `vendor/decimen-codec/decimen_codec.wasm` (281,113 B) and `.js` glue (53,467 B) are AGPL-3.0-or-later with source in a **separate repo**. If BNR hosts the receiver, the Corresponding Source duty reaches that artifact too — **mirror decimen-codec, not just the transfer repo**, or the Source pointer is only as durable as a second account BNR does not control.

**The decoder is an opaque committed binary — the primary supply-chain risk.** You cannot diff it; reproducing it means trusting or rebuilding a second project's toolchain. Partial mitigations (release `SHA256SUMS.txt`, codec self-identifies via banner + `version()`/`build()` exports) are not reproducible builds. **And it is pre-authentication native code parsing attacker-controlled pixels** — including a bespoke `readTracked` path that skips detection and samples the grid from a caller-supplied quad. A memory-safety bug there is reachable by pointing the camera at a hostile printed code. It runs in a worker, but on the same origin. **Not audited here.**

**Platform camera policy blocks the bootstrap direction you want.** iOS Safari and Android Chrome will not give a `file://` page a camera; `getUserMedia` is stripped from insecure origins entirely. **Any plan involving optical self-propagation of the receiver onto a phone assumes a capability that does not exist.**

**A literal `.bnr` TLD would break the camera.** No public CA will issue for a non-public TLD; without a publicly-trusted cert the receiving phone has no secure context and `getUserMedia` does not exist. An internal CA works only for devices that already trust it — destroying the frictionless-onboarding property for exactly the new user the founder named. **Use a real, publicly-resolvable HTTPS hostname for anything a stranger's phone must reach.** *(Reasoned from the documented secure-origin constraint; the naming itself is BNR-side.)*

**Auto-show is ON by default** on the receiver, so a landed payload displays itself on a phone someone may be holding up in a room. **Any BNR-hosted receiver must ship this OFF for identity payloads.** Received media is also staged in a same-origin Cache API entry that **outlives the tab**; clearing is discretionary. Never let a ceremony payload reach that path.

**Gzip inflation runs before the SHA-256 gate** (`unpackFile` at `receive/main.ts:1105` precedes `verifyFile` at 1106). The bounding is excellent, but it is still pre-authentication code operating on attacker-supplied compressed data.

**`rnd() % k` modulo bias** in `frameIndices` and `repairIndices` (`shared/fountain.ts:126, 154`). Benign for erasure coding; **not** benign if frame seeds were ever repurposed as nonce or key material in a BNR profile.

**Doc/code divergence on the fountain, and 4× stale size figures.** The prose still describes robust-soliton LT; the code ships a systematic carousel. `install-and-offline.md` says sender "~55 KB" (now 226,647 B), receiver "~1.3 MB" (now 992,317 B — the 1.3 MB figure matches v0.3.0), decoder "940 KB" (now 281,113 B); `sending.md` says snippets cap at 16 KB (really 4 MiB). **If BNR sizing decisions get made from the prose docs rather than the release assets, they will be wrong.** For BNR, the golden vectors — not the prose — are the actual contract.

**Wire format has broken twice in twelve days, under unilateral control.** v1 magic `0x0C` (v0.3.0) → v2 magic `0x0D` (v0.4.0) → v3 magic `0xD1 0xC3` (v0.5.0, 2026-08-12), each an intentional hard break. `troubleshooting.md`: "0.5.0 changed the frame format and is not compatible with 0.4.x." A saved standalone HTML interoperates with its own vintage forever but not with a newer peer. `shared/protocol.ts`'s own comment says silent breaks are "NOT survivable once store binaries are in the field." Against the 10^10 × 1000yr filter this is the central fragility: **v3's design is the right fix, but it is days old and unproven, and every BNR flow pinning a saved standalone file inherits a format expiry date.** Pin an exact tag, verify `SHA256SUMS.txt`, treat that snapshot — not upstream — as BNR's contract. Do not track main.

**Key-person and continuity risk.** Sole copyright holder is one natural person behind a pseudonym; repo is ~15 days old; **exactly one contributor has ever signed the CLA**; no entity, no foundation, no escrow, no succession clause anywhere in either CLA. The AGPL grant is irrevocable and survives him; **the commercial exception, wire-format governance, decimen.app, and the vendored-decoder source repo do not.** 6024 stars in two weeks is attention, not maturity. **Bus factor is 1.**

**Upstreaming a patch hands over commercial relicensing rights.** CLA §2 lets the Maintainer sell BNR's contributed code under proprietary terms to anyone, including competitors, forever. §3 guarantees it also stays AGPL, but does not stop the commercial track. **Contribute only cosmetics BNR does not mind a competitor selling** — translation review (CONTRIBUTING.md calls it "the single most useful small contribution this project can take") and device/browser decode bug reports, which need no CLA. Keep protocol hardening, encryption layers, and ceremony integration out of upstream PRs.

**The CLA workflow runs third-party code under `pull_request_target`** with `contents/actions/pull-requests/statuses: write`. Correctly mitigated by SHA-pinning, but worth knowing if BNR ever forks the workflow or trusts CI artifacts from this repo.

**Raising error correction at the default frame size is arithmetically impossible.** 2953 B is QR V40 byte-mode capacity at ECC L; V40 at ECC M holds 2331 (which is why 2331 is in the dropdown). A user reaching for "more error correction" while leaving bytes/frame at 2953 has asked for something no QR version can encode — **and the settings UI offers the combination.** The failure path was not read.

**One-way means no negotiation and no receipt.** The sender never learns whether the receiver got it; the stream loops forever. Any ceremony needing bilateral confirmation requires a second optical leg with roles swapped — doubling acquisition cost and requiring both devices to have cameras and screens.
